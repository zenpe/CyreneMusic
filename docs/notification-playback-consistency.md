# 通知播放状态一致性修复

## 实施范围

- `JustAudioEngine` 为恢复请求维护独立版本。暂停、停止、换源、释放播放器会使旧恢复请求失效；异步音量/EQ 准备结束后，失效请求不能调用 `play()`。
- 恢复请求版本与原有音量恢复 `_playTicket` 分离，取消恢复后仍保留需要恢复音量的标记。
- 首播、预加载激活继续走原来的启动等待流程，不把正常暂停变成启动超时；控制队列不等待 `just_audio.play()` 的整个播放生命周期。
- `PlaybackService` 为用户控制操作维护版本，恢复会话加载完成后不能覆盖较新的暂停/停止意图。待确认的控制意图只服务于通知表达，不替换全局 `desiredPlaying` 语义。
- 通知使用统一的只读映射计算按钮和 `playing/processingState`。加载中的播放意图显示暂停操作，稳定状态下的系统暂停仍然显示播放操作。
- 所有状态更新入口使用同一映射；播放控制立即发布，进度保留一秒刷新，iOS 保留原有强制刷新。封面队列不能阻塞控制状态，旧封面查询不能发布到新曲目。
- 原包名、通知渠道、图标、前台服务配置与 `PLAY_PAUSE` 操作通路保持原配置。

## 自动化证据

修复前，使用受控原生播放器替身、实际 `JustAudioEngine` 和 `EngineHost` 执行测试：

1. 恢复准备期间暂停：仍调用了一次 `play()`，测试失败。
2. 暂停后再次恢复：调用了两次 `play()`，测试失败。
3. 恢复准备期间停止：仍调用了一次 `play()`，测试失败。

修复后以上测试通过。新增测试还覆盖再次恢复时的最新音量、换源取消、首播与预加载激活、通知意图更新、定时器一致性、明确播放/暂停指令、系统暂停的状态映射、慢封面及旧媒体结果、倍速变化和停止状态。

验证命令：

```text
flutter test test/services --reporter expanded
```

实施时服务层共 153 个测试通过。播放器替身控制的是音量异步等待；没有用桌面测试冒充 Android 原生 EQ、音频焦点或 SystemUI 验证。

## 发布前真机验收

以下尚需实际设备验收，不能由 Dart 测试替代：

| 操作 | 预期 |
| --- | --- |
| 冷启动但不播放 | 不额外创建播放通知 |
| 首播，随后退后台/锁屏 | 通知出现且暂停操作可用 |
| 通知暂停后恢复，多次快速交替 | 最后一次操作生效，按钮最终一致 |
| 开启 EQ，快速恢复后暂停，再恢复 | 不自行播放，再次恢复有声音且音量正确 |
| 慢网络切歌期间暂停 | 加载完成后保持暂停 |
| 播放失败、自动下一首、列表结束 | 会话与按钮状态正确，不误触发无关重试 |
| 来电/音频焦点中断及中断期间手动暂停 | 符合既有中断策略；确认手动暂停不会被自动恢复覆盖 |
| Windows 播放、暂停、恢复及会话恢复 | 共享播放控制改动不影响原有行为 |

本次保留 just_audio 的音频焦点管理，没有新增第二套中断恢复策略。系统中断期间手动暂停属于必须验收的原生边界，状态映射测试并不证明该原生行为。
