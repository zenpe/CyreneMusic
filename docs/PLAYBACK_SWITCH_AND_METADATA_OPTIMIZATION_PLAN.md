# 切歌与歌曲信息链路优化方案

> 本文档聚焦一个问题：为什么切歌时仍然会慢，以及应该如何把“可播放链路”和“补全链路”彻底拆开。
>
> 更新时间：2026-03-19

## 1. 目标

本方案只追三个结果：

- 点击切歌后，主播放器立即进入目标曲的切换事务
- 音频主链路只等待“可播放最小描述”，不等待歌词或冗余元数据
- 歌词、封面、专辑信息、缓存写回全部改成后台补全，不污染当前播放

## 2. 当前实现结论

现状不是“歌词缓存拖慢了切歌”，而是“歌曲详情获取仍然可能拖慢切歌”。

更准确地说：

- 本地缓存命中时，歌词和歌曲信息都能直接从 `.cyrene` 元数据返回
- 本地缓存读取本身只做索引匹配和文件头校验，通常不是主要耗时
- 真正会阻塞切歌的是 `SongDetail` 主链路网络请求
- 对洛雪和 TuneHub，客户端已把“单独歌词请求”从播放主链路移除
- 对 OmniParse 类接口，如果后端在一个接口里同时组装 URL、歌词、完整元数据，那么客户端仍然必须等待整包返回

结论：

- 当前最大优化空间不在“本地歌词缓存”
- 当前最大优化空间在“把歌曲详情拆成可播描述和补全描述”

## 3. 当前链路拆解

### 3.1 切歌主链路

当前切歌事务的主流程是：

1. `prepareTarget`
2. `resolveSongDetail`
3. `resolvePlayableSource`
4. `commitPlayback`
5. `commitPresentation`

主阻塞点在 `resolveSongDetail`。

如果缓存命中：

- 直接读取 `.cyrene` 头部元数据
- 构造 `SongDetail`
- 进入可播放源提交

如果缓存未命中：

- 走 `MusicService.fetchSongDetail()`
- 等待返回可播放 URL
- 然后才继续播放

### 3.2 歌词链路

当前歌词来源分 3 类：

- 缓存元数据中的歌词字段
- `fetchSongDetail()` 直接返回的歌词字段
- 切歌完成后的后台补全请求

其中：

- 洛雪 / TuneHub 的同步歌词拉取已改为可关闭
- `playback` 和 `preload` 现在只拿可播信息
- `cache-refresh` 才会后台补歌词并回写缓存

### 3.3 缓存链路

当前 `.cyrene` 缓存同时存两类内容：

- 音频数据
- 元数据

元数据包含：

- 标题
- 歌手
- 专辑
- 封面
- 原始 URL
- 音质
- 歌词 / 翻译 / 逐字歌词

这意味着：

- 命中缓存时，主播放器展示信息理论上可以完全不依赖网络
- 但首次播放时，缓存写入仍然是“播放后后台再整首下载一次”

## 4. 什么会阻塞切歌

### 4.1 会阻塞

- 缓存未命中时的 `fetchSongDetail()` 网络耗时
- 桌面端代理不可用时的回退判断
- 某些后端接口把 URL、歌词、完整元数据绑在一起返回时的整体响应时间

### 4.2 原则上不应阻塞

- 本地缓存元数据读取
- 歌词补全
- 封面补全
- 主题色提取
- 后台缓存写入
- 预取结果保存

### 4.3 当前仍存在的结构性问题

虽然客户端已经把洛雪 / TuneHub 的同步歌词请求移出主链路，但还有两个结构性问题未彻底解决：

1. `SongDetail` 仍然是“大对象”
2. 预取结果仍偏向“详情预取”，不是“可直接提交给引擎的播放计划预取”

## 5. 最佳优化方向

## 5.1 第一优先级：把 SongDetail 拆成两层

这是收益最高、最值得投入的优化。

主链路不应再等待完整 `SongDetail`，而应只等待一个最小可播描述：

- `url`
- `headers`
- `sourceType`
- `contentType`
- `duration`（可选）
- `coverUrl`（可选）
- `metadataReady`

推荐新增一个轻量结构，例如：

```dart
class PlaybackDescriptor {
  final String url;
  final Map<String, String> headers;
  final String sourceType;
  final String contentType;
  final Duration? duration;
  final String? coverUrl;
  final bool metadataReady;
}
```

然后把完整歌曲信息降级为后台补全对象，例如：

```dart
class SupplementalSongMetadata {
  final String title;
  final String artist;
  final String album;
  final String lyric;
  final String tlyric;
  final String yrc;
  final String qrc;
}
```

主链路只依赖 `PlaybackDescriptor`。

## 5.2 第二优先级：给后端增加轻量播放接口

如果后端继续提供“大而全”的 `/song` 接口，客户端最终还是得等整包返回。

建议增加轻量播放接口：

- `/playback/resolve`
- `/qq/playback/resolve`
- `/kugou/playback/resolve`

这些接口只返回：

- 可播放 URL
- headers
- 实际 source 类型
- 是否命中代理或缓存策略

歌词和完整元数据改成：

- `/metadata/song`
- `/lyrics/...`

原则：

- 播放接口只解决“能否播”
- 元数据接口只解决“展示是否更完整”

## 5.3 第三优先级：把预取升级成可直接提交的播放计划

当前预取方向是对的，但还可以更进一步。

预取不应只保存“下一首详情”，而应保存“下一首可直接提交的 plan”：

- `PlaybackDescriptor`
- 已解析 headers
- 代理 URL
- 是否缓存命中
- 可直接构造的 `PlayableSource`

目标效果：

- 点击下一首时，不再现场做 URL 解析
- 切歌时直接命中 `commitPlayback`

推荐目标：

- 顺序播放时，下一首大概率命中预取 plan
- 用户连续快切时，只消费最后一次有效 plan

## 5.4 第四优先级：坚持 stale-while-revalidate

对展示信息要采用“先展示、后补全”的统一策略。

规则：

- 有缓存元数据就立刻展示
- 有 `Track` 基础信息就先展示
- 缺歌词、缺专辑、缺封面时，不允许重新把这些工作拉回主链路
- 一律后台补全并校验事务 token

这样可以避免：

- 为了拿歌词而延迟出声
- 为了拿高清封面而延迟播放
- 为了补专辑信息而让切歌回到 loading

## 5.5 第五优先级：把缓存从“二次下载”升级为“边播边落盘”

当前缓存写入模型是：

1. 当前曲先播放网络流
2. 后台再次发起整首下载
3. 下载完成后写 `.cyrene`

这有三个问题：

- 增加带宽开销
- 缓存出现得晚
- 容易与预取竞争

更优方案是：

- 桌面代理流或引擎适配层直接复用首播流量
- 边播边写加密容器
- 播放结束前尽量完成落盘

目标：

- 第一次播放结束时，缓存通常已经可用
- 第二次播放直接命中本地缓存

## 6. 不建议优先优化的方向

以下方向不值得放在最前面：

- 继续抠本地歌词读取性能
- 再缩短一些 timeout
- 用更多 loading 动画掩盖切歌慢
- 在 UI 层做更多乐观假数据而不处理后端等待链路

原因很简单：

- 症状在“请求太重”
- 根因在“主链路等待太多”

## 7. 建议实施顺序

### 阶段 1：主链路最小化

- 抽出 `PlaybackDescriptor`
- `resolveSongDetail` 改成 `resolvePlaybackDescriptor`
- `commitPlayback` 只依赖最小可播描述

验收：

- 切歌日志里 `resolveSongDetail` 耗时显著下降
- 歌词接口再慢也不影响出声

### 阶段 2：后端接口拆分

- 新增轻量播放解析接口
- 客户端只在主链路调用轻量接口
- 歌词与展示补全改成后台接口

验收：

- 日志中先出现播放提交，再出现歌词完成
- 主链路请求包体更小、响应更快

### 阶段 3：预取 plan 化

- 预取结果从“详情对象”升级为“可播放计划”
- 下一首预取直接缓存 `PlayableSource` 描述

验收：

- 顺序切歌大量命中 prefetch
- 切歌事务更多时间花在 `commitPlayback`，更少花在网络解析

### 阶段 4：边播边缓存

- 让代理流或引擎适配层支持落盘
- 减少首播后二次整首下载

验收：

- 缓存管理里能更快看到实际缓存文件
- 后台缓存日志从“二次下载完成”转向“流式落盘完成”

## 8. 最终判断

当前最佳优化策略不是继续围绕“歌词缓存”做微调，而是：

1. 把主链路等待的数据压缩到最小
2. 把完整歌曲信息和歌词彻底移到后台补全
3. 把预取升级成可直接播放的 plan
4. 把缓存升级成边播边落盘

一句话总结：

切歌快的关键，不是“歌词要不要缓存”，而是“主链路只做让声音出来这件事”。
