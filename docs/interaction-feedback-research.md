# 客户端操作反馈调研与体验方案

日期：2026-10-30。对象：CyreneMusic 1.3.6，Windows 桌面与移动端的 Material、Fluent、Cupertino 界面。

## 1. 推荐结论

采用“就地状态优先，短提示补充，失败可处理”的统一规则。先减少不必要的提示，再统一保留下来的提示的视觉和行为。

普通播放、暂停、切歌、收藏、设置开关通过控件和页面状态反馈；加入队列、复制等结果不在当前视野内的操作保留简短确认；登录、表单、推荐和导入失败优先在相关区域显示可处理的结果。只有确实需要用户决定的事项使用确认弹窗。

统一的是反馈规则和入口，三套主题保留各自的字体、表面色、圆角和控件风格。无需新增设置开关、通知中心、消息数据库、后端接口或第三方提示库。

## 2. 调研方式与结论边界

- 静态扫描当前客户端 lib 目录，抽查播放、歌单、收藏、登录、服务器设置、账号绑定、音源、存储、下载和全局错误通路。
- 查阅当前依赖 fluttertoast 9.0.0 的排队实现及 Flutter ScaffoldMessenger 文档。
- 阅读 Material、Apple、Microsoft Fluent 与 W3C 状态消息资料，比较本地 Q-music 的相关实现。
- 本次未改业务代码、未执行构建或测试，也未做三主题真机录屏和用户实验。调用数量是静态源码统计，包含主题分支、开发者页面和可能保留的旧入口，不能直接代表用户实际见到的频率。

## 3. 当前项目的主要发现

### 3.1 多种反馈机制并存

| 机制 | 静态调用数 | 分布 | 观察 |
| --- | ---: | ---: | --- |
| showSnackBar | 186 | 50 个文件 | 各页面单独决定颜色、文案、时长，缺少统一策略 |
| ToastUtils | 20 | 8 个文件 | 成功、错误和居中模式提示共用工具，普通提示缺少统一去重/替换 |
| Fluent displayInfoBar/showInfoBar | 11 | 8 个文件 | 与 SnackBar 混用，部分是操作反馈，部分是状态反馈 |
| SnackBarAction | 1 | 1 个文件 | 当前主要在音源操作失败时提供重试，不应假设其他提示已有撤销或重试能力 |

186 个 SnackBar 构造与 186 个 showSnackBar 是同一类调用的两种统计，不能相加。页面内固定 InfoBar 不计入上表第三行。

### 3.2 播放状态与操作提示重复

通用歌曲行点击后会显示“正在加载：歌曲名”；日推详情播放单曲、播放全部会显示“开始播放”。迷你播放器本身已经承担曲目、加载和播放状态展示。

同时 main.dart 注册了播放最终失败和 notice 的全局 Toast 回调，播放器页还有内嵌错误区域。因此，页面自行报告播放结果和播放服务集中报告结果存在重复、顺序不一致的风险。应由实际播放状态表达结果，页面不以 playTrack 的 Future 完成作为“已经出声”的证据。

### 3.3 蓝黑色并非唯一根因

Material 主题当前没有统一的 SnackBarTheme，主要使用 Material 3 的默认配色；Fluent 的 Material 兼容主题另有 SnackBar 配置。部分页面又写死绿色、红色或蓝色背景。

ToastUtils 的自定义浮层使用固定蓝/绿/红强调色和背景模糊，与其他提示的表面、大小、位置并不一致。具体用户看到的某条蓝黑色提示，仍需要结合截图或触发动作才能确定来源，不能单靠颜色认定组件。

### 3.4 连续操作容易遗留旧提示

Flutter showSnackBar 在已有提示时会排队；当前 FToast 的 _overlayQueue 同样会顺序显示。ToastUtils 普通、成功、错误入口未统一清理旧队列，居中提示只移除当前项；页面只有少数位置主动隐藏当前 SnackBar。

这解释了连续操作后提示可能继续出现的机制。全局“只显示一条”还需要明确哪些可以替换、哪些不能丢失，不能简单地清空所有错误或撤销操作。

### 3.5 部分提示层级不合适

- 歌曲操作菜单的 Cupertino 提示使用 showCupertinoModalPopup：一次简单确认也会引入模态路由，与轻量、不阻断的反馈目标不符。
- 部分服务器地址校验通过底部提示展示，而错误应贴近输入框，保留输入并让用户立即修正。
- 登录成功后页面已经跳转，额外成功条通常没有必要；失败应留在登录页。
- 网易云扫码包装函数与设置页外层均含绑定成功提示入口，同一路径应由一个页面负责最终确认，避免备用扫码流程出现重复成功反馈。
- 下载已有任务状态及系统完成通知；不能把全部任务反馈都机械迁移为应用内 Toast，系统媒体控制也应保留现有语义。

### 3.6 已有适合复用的基础

- 播放服务已有结构化问题、恢复动作和最终失败边界；无需为提示重写播放控制或增加第二条重试链。
- 网易云歌单导入按条显示结果，适合作为长任务反馈范例。
- 音源设置已有失败后的重试按钮。
- FloatingPlaybackInsets 已抽象部分底部播放区域占位，可作为位置计算的依据之一；仍需覆盖其他桌面、Material 和弹窗布局，不能直接认定所有界面均已适配。
- 已有 Toast 上下文切换回归测试，可以在实施时扩展生命周期测试。

## 4. 官方规范与同类实现

| 来源 | 实际查阅到的原则 | 对本项目的意义 |
| --- | --- | --- |
| Material Snackbar | 暂时、非打断、在操作发生的界面上下文内展示；可附带撤销等动作 | 保留有必要的短反馈和行动入口，不给每个点击都发成功条 |
| Apple Feedback | 状态靠近相关对象；重要任务才需要额外成功确认；Alert 的打断程度应匹配事项重要性 | 设置、播放及收藏优先就地反馈，不用模态弹层扮演 Toast |
| Microsoft InfoBar | 适合可见、非打断且较长期的状态；避免快速反复出现消失 | 账号过期、音源不可用可在区域内持续显示；不把所有成功提示换成 InfoBar |
| Flutter showSnackBar | 已有提示时新增消息会进入队列；浮动位置只自动避让 Scaffold 认识的底部组件 | 要主动定义去重与替换；自定义悬浮播放器需要明确避让 |
| W3C 状态消息 | 重要状态变化应可被辅助技术感知，且不需要抢焦点；不要求制造更多状态文案 | 少弹条同时保留可访问的状态语义，避免把重要错误变成转瞬即逝的视觉文字 |

本地 Q-music 的启发：队列中点歌使用行内 busy 状态，失败才 Toast；批量加入歌单有忙碌状态和防重复提交。它仍大量使用 Android 原生 Toast，固定偏移和平台样式不能直接照搬到本项目的桌面与多主题环境。

- [Microsoft InfoBar](https://learn.microsoft.com/en-us/windows/apps/design/controls/infobar)

## 5. 推荐的场景规则

| 场景 | 默认反馈 | 失败或特殊情况 |
| --- | --- | --- |
| 播放、暂停、切歌、日推播放、FM 换批 | 播放器/卡片的加载、曲目和按钮状态；成功不弹条 | 最终失败由播放问题通路统一处理；自动换源、重试中不连续报错 |
| 收藏/取消收藏 | 图标、收藏数量或列表即时变化 | 保存失败回退状态，必要时一条失败提示；不能只隐藏失败 |
| 播放模式切换 | 更新图标；图标含义不明显时，按钮附近短暂显示“单曲循环”等名称 | 连点只保留最后模式，不每次居中弹出 |
| 下一首播放/加入队列 | 当前界面通常看不到结果，可显示“将在下一首播放”“已加入队列” | 同一批操作合并计数；失败明确说明未加入 |
| 复制链接、导出 | “已复制”等短提示，或任务完成状态 | 错误保留可操作的重试/位置说明 |
| 普通设置开关、音量 | 控件变化即反馈 | 持久化失败显示并恢复一致状态；音量可保留原有专用交互反馈 |
| 清理缓存、同步歌单、检查更新 | 原按钮忙碌，结束后就地展示结果/新数值 | 不允许重复触发；失败提供重试，不持续刷全局错误 |
| 登录、服务器地址输入 | 输入区附近校验；成功跳转或显示保存后的地址 | 留在原页面，保留输入，指出错误；地址切换不代表服务已经连接成功 |
| 网易云绑定/解绑 | 返回后更新昵称、头像和绑定状态；必要时只确认一次 | 绑定页就地错误；过期展示“重新绑定”，不退出 Cyapi |
| 推荐页、搜索、发现加载 | 对应区域加载/空状态 | 出错区域就地“重试”；空结果和请求失败必须区分 |
| 歌单导入、批量任务 | 持续进度及成功/失败摘要 | 部分失败保留条目结果与仅重试失败项的入口，不逐项弹条 |
| 从歌单移除歌曲 | 列表变化；有可靠恢复能力后可提供“已移除 · 撤销” | 当前不能假设接口支持恢复原顺序和位置；未实现前沿用可靠确认与失败处理 |
| 删除整张歌单、清空历史、解绑 | 按实际可恢复性决定是否需要确认；成功通过页面变化反馈 | 不以 Toast 替代不可恢复操作的必要确认 |
| 全局离线、账号失效、音源未配置 | 一个相关区域的可见状态和恢复入口 | 不让各请求重复弹同一错误；区分 Cyapi 登录失效与网易云绑定过期 |
| 后台下载与媒体播放 | 现有任务页、系统下载通知与媒体会话 | 前后台反馈协调，避免同一结果同时多处打断；不为普通操作请求系统通知权限 |

## 6. 视觉、位置与无障碍

### 三套主题

Material 使用主题化浮动 SnackBar；Fluent 使用贴合其表面、细边框和字体的非模态短浮层；Cupertino 使用圆角、中性表面、无模态遮罩的短浮层。页面内持续提示分别使用主题匹配的状态组件，Fluent 可复用 InfoBar。

普通短提示不使用整块高饱和蓝/绿/红背景，不默认增加昂贵的背景模糊。颜色取自当前主题：中性底色、高对比正文，必要时用小图标表达成功或警告；严重错误可有较明显的错误标识，但仍需文字说明。

桌面建议最大宽度约 420–480 逻辑像素；手机左右留约 16 逻辑像素。圆角沿用主题令牌，避免为所有主题强行指定同一个数值。普通文案以一行、最多两行为目标，必要信息不能只靠省略号隐藏。

### 空间与交互

- 普通短提示位于当前界面下方的可用区域，避开迷你播放器、底部导航、系统手势区和键盘，不遮挡进度条、暂停或切歌按钮。
- 输入错误在输入框附近；弹窗内部错误留在弹窗中，避免浮在弹窗背后。交互式提示必须处于正确的交互层级。
- 过于狭窄或键盘展开后无空间时，改用就地反馈，不靠不断提高 z-order 掩盖布局问题。
- 普通确认不抢焦点，不创建模态路由，不阻止继续点歌。不要给整个屏幕盖一个透明点击层。
- 保留现有用户主动操作的触觉反馈即可，不给每条提示再加声音或震动。

### 时长

- 无动作的短确认以约 2 秒为初始值；极短的辅助标签可约 1.5 秒。需要结合长文本和实际设备验证，不能全局硬编码为 1 秒。
- 可修复失败优先留在原区域；补充性的失败短提示可约 4–6 秒，避免只闪一下就失去原因。
- 带重试/撤销的反馈不能套用普通成功时长；至少提供合理操作时间，并尊重系统无障碍时长偏好，键盘焦点或鼠标悬停时不要自动关闭。
- 长任务不依赖短提示显示进度。

短提示需要 live region/合适的语义播报，但不挪走输入焦点。移除收藏弹条时，也要通过控件状态和语义让读屏知道“已收藏”。支持字体放大、减少动态效果和浅深色高对比；不能仅靠红绿区别结果。

## 7. 去重、优先级与生命周期

1. 一次操作只有一个最终反馈负责方。播放最终失败由既有播放问题通路负责，页面不再追加自己的播放成功/失败条；绑定成功由调用页或流程统一负责。
2. 全局临时提示同一时间最多一条。普通信息不积压 FIFO 队列，同类更新替换；仅内容相同且没有独立业务含义的提示才去重。
3. 对不同歌曲或不同任务的真实失败，不应仅因文案相同就全部吞掉；保留项目范围和操作标识，批量失败用摘要承接。
4. 新的普通提示不能顶掉需要处理的错误或尚有效的撤销动作。必要时普通确认不展示，页面内仍保留实际状态。
5. 页面切换后，取消旧页面待显示的普通提示；用户、后端、账号绑定或主题切换时，旧上下文反馈不得带到新上下文。全局播放问题只跟随仍有效的播放操作。
6. 成功反馈基于业务实际结果，不能把“按钮已点击”“请求已发出”“地址已保存”说成任务成功。
7. 应用后台不排队积攒普通成功提示；回到前台呈现当前真实任务状态。全局登录跳转保留现有统一处理，不重复叠加过期弹条。

## 8. 最小实施结构与优先级

不建立新的业务事件总线。增加或收敛为一个小型 AppFeedback 入口，集中处理短提示的类型、去重、操作标识、时长、主题和层级；页面内错误/进度继续由对应页面状态承担。复用现有播放问题和主题系统，迁移完成后清理失去用途的旧 Toast 包装，是否移除依赖另按真实引用检查决定。

### 第一批：直接改善高频体验

- 删除播放/暂停/切歌成功及明显重复的收藏、普通设置开关提示。
- 保留并统一队列、复制、播放模式等必要确认。
- 停止普通提示排队，消除 Cupertino 模态 Toast。
- 播放最终失败只保留一个负责通路；修正重复绑定成功提示。
- 统一短提示主题和播放器避让，覆盖 Material 与 Fluent，移动 Cupertino 一并适配。

### 第二批：让失败和长任务更好处理

- 登录/服务器输入错误就地展示。
- 绑定、推荐、同步、缓存清理和批量导入统一忙碌/结果/重试语义。
- 全局断网及账号失效去重，保留具体区域的恢复入口。
- 重试只调用原有操作，不在提示层增加第二套重试机制。

### 第三批：需要数据能力配合的增强

歌曲删除撤销单独评估本地/服务器歌单的恢复契约、顺序、重复项与并发；没有可靠契约前不提供假撤销。这不是第一批视觉收敛的前置条件。

不新增“关闭所有提示”设置来让用户处理产品自身噪声，也不一次性对全部 186 处进行机械替换。应按真实调用链逐项分类，开发者诊断提示最后处理。

## 9. 验收标准

- 连续播放/切歌 20 次，播放器状态正常，不出现对应数量的成功弹条，不遗留旧歌曲的加载提示。
- 连续切换播放模式仅显示最后状态；下一首播放仍有可理解的确认。
- 加入多首队列不会堆满提示；合并反馈不丢失实际加入数量。
- 最终播放失败只产生一次主要外部反馈；若旧歌曲仍在播放，不能误报全播放器已停止；请求取消和中间重试不当作最终错误。
- 推荐为空与请求失败明显不同，重试操作可用，错误不被下一条普通成功提示覆盖。
- 绑定/解绑、扫码与网页登录路径不重复提示；后端切换或退出后没有旧账号提示出现。
- 登录和服务器输入失败保留输入、就地解释，不在错误后弹“操作成功”。
- 手机 320 逻辑像素宽、横屏、键盘展开、弹窗与迷你播放器同时存在时，无溢出、无遮挡关键控件。
- Material/Fluent/Cupertino、浅深色、放大字体、TalkBack/VoiceOver/桌面键盘焦点符合以上行为。读屏不被逐首播放通知打断；关键失败仍可感知并处理。
- 同步/导入的部分失败可定位且可重试；关闭页面后不继续刷全局结果。
- 现有系统媒体通知、后台播放、下载与登录过期恢复不因提示整理而改变。

目标是用户能持续知道“现在是什么状态、失败后怎么办”，同时不必逐条阅读已经能从界面看出的普通成功结果。具体时长和位置为初始设计值，最终以一次集中的 Windows/Android 实机验收调整，不以静态调研替代真机结论。
