# 按平台自动推荐音源实施方案

> 当前规则已简化（2026-11-17）：首次检测合格即发布；正常推荐继续使用；异常一分钟后复测一次，仍异常才找替代；找到替代并发布后结束该平台本轮搜索。日常只检测当前源，其他候选低频检测。原候选多轮确认与覆盖增益比较已移除，下面保留的是 v0.0.18 的历史设计与实施记录；当前后端规则见 [运维说明](https://github.com/zenpe/cyapi-go/blob/master/docs/15-automatic-source-recommendations.md)。客户端清单协议和播放流程不变。

- 日期：2026-11-16。
- 状态：两端代码已实施；本地回归验证完成情况见第 10 节。尚未部署启用，NAS 首轮运行与客户端实际播放属于上线验收。
- 复核：2026-11-16；最终实施基线，已补齐证据有效期、更新重试、音质贯通、发布事务和新旧归档回收约束。
- 范围：`F:/cyapi-go` 与 `F:/CyreneMusic`。
- 目标：用户选择一次自动推荐后，后端持续检测并维护 QQ、网易各自的推荐脚本，客户端自动取得并应用；日常不依赖管理员逐项检查、手动发布。

## 1. 产品与工程决策

1. 按平台推荐，首版仅支持 QQ、网易标准音质 128k。
2. 允许部分测试歌曲失败。通过率用于展示，自动替换依据同样曲目的检查覆盖或可验证证据增加及持续表现，不设固定通过率资格线。
3. 同一首歌在多个脚本上失败，保留覆盖记录，不自动删除样例，也不一票否决整个渠道。
4. 复用现有 Goja worker、资源检查、脚本归档和本地 QuickJS；首版不增加 FFmpeg、Node、数据库表或独立服务。
5. 后端选择脚本，客户端本地解析；后端不代理用户的实时解析和音频流量。
6. 发布明确的按平台清单，客户端做一次适配；不把不同第三方脚本拼接成一个 JavaScript 文件。
7. 首版不增加客户端失败后遍历备用脚本、跨平台搜索同曲或额外播放重试。
8. 新能力按完整闭环交付一次，按后端兼容接口、客户端适配、自动启用的顺序上线，不为每个开发步骤发布发行版。

“符合资源检查条件”只描述已有结构、时长和重复资源证据，不称为已解码或歌曲身份已验证。

## 3. 检测证据与评估规则

### 3.1 每轮必须可比较

自动评估使用 `state=completed` 且 `completed=planned` 的完整报告，并要求 worker 实际具有内存硬限制；显式未隔离的手动诊断不进入自动发布。每个平台须满足可配置的最小样例数量，按不同 TrackID 去重；不足时显示“样例不足”，保持已有推荐。

一轮比较中，所有参与脚本使用同一平台、128k、样例集合版本和检测器版本，每首恰好一项结果。脚本身份为目录路径与内容 SHA256。初始化失败或不支持仍保存每首结果，不能漏项后得到较高比例。

不直接复用管理列表从多个历史报告拼接出来的汇总作为决策输入。定向巡检只比较该轮实际检测的脚本；原始报告不因推荐政策变化而改写。

首次启用时复用现有详情获取能力自动补全已有样例的平台标识和时长，防止旧样例与客户端输入长期不一致。上游详情请求失败时保留原样例、记录刷新异常并定时重试，不把它记成脚本失败；字段发生实际变化才创建新样例版本，不能因刷新时间戳变化反复清零确认进度。

### 3.2 派生评估，不改变原始 outcome

| 评估项 | 定义 | 用途 |
| --- | --- | --- |
| `N` | 本平台本轮启用样例总数 | 所有脚本使用相同分母，不能删去失败、未验证或不支持项 |
| `P` | 结构可识别，非疑似短资源、非跨歌曲可疑重复 | 资源检查符合项数量，同时保留对应歌曲集合 S |
| `V` | `P` 中预期与实际时长均可靠，且现有时长评估为 no_short_duration_detected | 有可靠时长依据、未发现明显偏短的子集，用于初次选择和候选排序 |
| `F` | 明确的初始化、解析或资源失败，且该失败不涉及检测限制 | 原始失败与诊断，不单首否决 |
| `E` | 失败涉及 probe 限制、执行环境故障、预算中断等 | 本轮不能据此证明脚本比另一脚本更差 |
| `U` | 已取得地址但资源未验证 | 不计入 P，也不称为已证明失效 |

复用现有 music.AssessAudioDuration 和可靠时长来源，不另加一套固定百分比/秒数的匹配阈值。时长未知的结构可识别资源可以计入 P，但不计入 V；V 也仅说明未发现明显偏短，不证明音频完整、时长精确相同或歌曲身份正确。

重复资源是警告而非歌曲错误的证明。首版保守地将涉及不同歌曲相同完整文件的项目排除出 P，不判定哪一首一定错误，也不判整个脚本失效。

某个备用请求被限制、最终仍取得符合条件的资源时，结果仍可计入 P；只将最终失败且涉及限制的结果归入 E。混合失败同时保留上游业务错误与 probeIssues，不能只剩“检测环境失败”。

### 3.3 最小证据与逐曲比较

不设 `P/N >= 某固定比例` 的通用资格线。保留可配置的证据底线：最小样例数量、候选至少有多少首符合资源检查条件、确认轮数。初始默认分别为三首、两首、两轮；这些是收集证据的运行参数，不是“2/3 就可靠”的定义。改变参数更新 policy 配置指纹并重置未完成确认。

初次选择和维护候选列表时依次比较：P 更多、V 更多、涉及限制更少、路径与哈希字典序。先筛选满足证据底线及下述替换条件的候选，再排序提名，不能让一个排名高但会损失已有覆盖的脚本挡住其他合格候选。不把排名第一自动称为健康；始终展示实际 P/N、时长证据和局限。

已有推荐 A 时，针对同样曲目比较候选 B：

- A 符合检查条件的每首歌，B 本轮也必须符合。B 在这些歌上失败、未验证、不支持或受限制，都不能证明替换没有退步。
- B 至少新增一首符合检查条件、而 A 有明确负面证据或仅为 U 的歌。负面证据包括无检测限制的明确失败、不支持，以及已识别的短资源或可疑重复等。前者记录为“检查覆盖改善”，U→P 记录为“可验证证据增加”，不称 A 已失效；两者都须多轮确认。A 涉及检测限制 E 时不能制造优势；仅从时长未知的 P 变成 V 也不构成新增覆盖。
- A、B 都失败的歌不提供相对优势，仍完整记录在 N 中；共同失败不一票否决。
- 双方各有胜负、完全同分、仅速度或 V 改善时，首版保持现有推荐。暂不引入歌曲权重和复杂评分来强行选出赢家。

例如 A 通过甲、乙，B 通过甲、乙、丙，而 A 对丙明确失败，B 有覆盖优势；若 A 对丙仅未验证，则 B 增加了可验证证据，两者理由分别记录。若 B 只通过乙、丙，则互有胜负，保持 A。这比仅比较两个“2/3”更能解释替换理由，也避免未验证的旧推荐永久无法替换。

### 3.4 多轮确认与替换

1. 扫描或巡检发现满足最小证据量且具有上述逐曲优势的候选；没有当前推荐时，按排序选择待确认候选。
2. 每轮至少间隔十分钟，默认再做一轮确认，完整检测候选与当前推荐的启用样例；配置确认轮数可调整，不复用同一报告 ID。
3. 各轮的参与脚本哈希、平台、音质、样例版本、检测器版本和 policy 配置指纹一致。仅其他无关脚本变化不清零；参与输入或当前推荐改变则清零。各轮候选都满足证据底线、保持 A 本轮所有 P，并至少有一首相同歌曲持续构成上述新增证据，才替换，不能用每轮不同的偶然成功拼成持续改善。
4. 不要求所有结果都没有 E。E 不制造优势，U→P 按上述证据增加处理；A 的某首正面证据在 B 上变成 E/U 时，本轮也不能用于证明无退步。
5. 当前推荐相对发布时的同版样例失去已有正面覆盖，且有明确负面证据时标记 degraded；样例版本不一致则重新建立基线。环境限制标记受限，过期标记 stale，不能冒充已证明退化。
6. 没有完成确认的候选时保留最近脚本引用并继续巡检；没有初始推荐且证据不足时显示 unavailable。即使选出的是当前最佳，也展示有限的样例覆盖，不伪造全平台可用保证。

用于决策的报告完成时间默认不得早于当前时间六小时（evidence_max_age）；一次确认链的首轮开始到提交也不得超过该窗口。超时、取消、输入变化、相对优势消失或证据过期均重置确认；服务停机时冻结的旧进度不能直接用于发布。stale 使用相同的最近有效检查窗口判定，不撤销清单。时间判断由可注入时钟实现；系统时间回退时作废无法可靠比较的确认记录。不同脚本共用上游不视为独立证据，多轮只用于抑制瞬时波动。

报告中的 recognized 不等于真实播放成功；该政策自动比较检测证据，不能保证未测歌曲、其他音质或所有客户端网络正常。

## 4. 自动调度

首版建议初始参数：全量扫描每 72 小时；每个平台当前推荐及最多一个候选每三小时巡检；发现替换候选后最早十分钟复核。首次启用立即安排全量扫描，不等待 72 小时。周期可配置，验收时根据 NAS 耗时、流量及上游额度调整。

原先“28 脚本每天全扫、每小时当前加两个候选”的建议，在每平台三首样例时约产生 600 项 worker 任务/天，音频若每项读满 8 MiB，单音频读取就约 4.7 GiB，尚未计入脚本自身请求。不能忽视用户已遇到的上游额度不足。上述较低频默认值下，固定巡检约 96 项/天、全量单遍平均 56 项/天起；分组重复检查当前推荐、多轮复核和故障提前扫描另计，均需展示实际任务量和读取字节，不能把估算写成固定成本。

- 一个独立调度 goroutine，复用同一 Controller 和跨进程检测锁。一次只运行一个批次，批内仍只有一个 worker。
- 定向选择只扩展内部 RunOptions；现有 CLI 的单路径/单平台参数和管理页面操作保持兼容。Controller 的复用判等纳入完整选择，避免两个不同巡检误认同一任务。
- 手动任务和定时任务互斥。遇忙跳过当前调度机会，不堆积无界队列，也不取消正在执行的手动任务。
- 全量扫描是多个完整比较批次组成的周期：按平台分组，每组包含当前推荐（若有）及有限候选，使用同版全体启用样例。根据既有单 worker 最长四十秒预算限制每组计划项数，单组含启动余量不超过九十分钟；定向巡检同样预估，不能硬编码三十分钟而让合法的大样例集永远跑不完。不能从中断报告中抽取部分结果发布。
- 全量扫描每次最多执行三小时工作片段，剩余时间不足以容纳下一批预算时不再开批。持久化目录版本和游标，未完成部分后续继续，不能每次从目录第一项重来。片段结束仍未扫描完时最早十分钟后续跑，不等待下个 72 小时；周期起点按首次片段记录。目录变化重新核对待扫描身份，已变更哈希不得复用旧结论。
- 批内不抢占，批次边界优先处理已到期复核，其次巡检，再继续扫描；每组开始时固定当前推荐，提交前若其改变则该组不能发布，重新安排比较。长批次意味着故障发现存在延迟，管理页面显示实际进度及下次可运行状态。
- 持久化上次尝试、完成、下次到期、候选确认进度。重启清除 running 标记，不能在每次重启时无条件重测全量。
- 初次启用且无可用历史时，服务就绪后安排全量扫描；不阻塞 API 启动或客户端播放。
- 目录同步后不直接发布新脚本。新哈希重新验证，既有推荐继续引用归档旧版本，直到替换完成。
- 定向巡检必须能读取当前已发布的归档脚本；即使它已从源目录删除或同路径被新版本覆盖，也能与新候选比较。内部选择使用受控 catalog/published 引用，校验原始字节哈希，不接受任意文件路径。
- 当前推荐持续失去已验证覆盖且候补没有可替代项时，提前安排全量扫描，最低六小时冷却；不必等到次日，也不能每次失败都重测所有源。
- 停服取消调度并回收 worker；只 admin 关闭时，已启用的自动推荐仍运行。

`source_recommendation.automatic.enabled` 是部署总开关，默认 false，启用必须同时启用 `source_recommendation.enabled`，不要求 `admin.enabled`。配置不满足依赖时启动明确报错。首次部署启用后，管理员可在页面暂停/恢复，操作状态持久化；暂停停止新自动检测、复核与发布，正在运行的自动任务取消并回收，手动检测不受影响。关闭总开关同样不再调度，但保留已发布数据及公共读取能力；页面不能越过配置启动任务。

周期配置为 full_interval、watch_interval，高级证据配置为 min_samples、min_positive_samples、confirmation_rounds、evidence_max_age。最小数量不得为零，min_positive_samples 不得大于 min_samples，min_samples 不超过当前样例上限；confirmation_rounds 至少为二。间隔为正，evidence_max_age 必须容纳所配置确认轮数的十分钟最小间隔及实际批次预算；启动校验不能通过的组合给出具体字段错误，不能静默放宽证据规则。样例实际不足时属于 unavailable，不要求修改部署配置。

恢复上次调度时间需要同时持久化最近尝试，失败采用退避而非每分钟重试。当前默认的故障发现、复核、客户端下载合计可能需要几十分钟至数小时；长批次或客户端挂起会进一步延迟，首版不承诺即时自愈。

## 5. 数据、发布与兼容接口

### 5.1 独立清单

新增 `GET /lx/recommendation-plan`，成功响应直接返回以下 JSON（不混用旧接口的 recommendation 包装）：

```json
{
  "format": 1,
  "planId": "p-<不可变版本ID>",
  "quality": "128k",
  "targets": {
    "qq": {"path": "一般/A.js", "sha256": "<64位小写十六进制哈希>", "name": "A"},
    "netease": {"path": "优质/B.js", "sha256": "<64位小写十六进制哈希>", "name": "B"}
  }
}
```

脚本通过新增 `GET /lx/recommendation-scripts/{sha256}.js` 下载，仅允许读取已发布清单引用及保留期内的归档。SHA256 用于内容完整性检查；不称其为独立的发布方签名。

planId 格式固定为 `p-` 加 32 位小写十六进制随机 ID。清单包含至少一个目标，只接受 qq/netease 和 128k；客户端拒绝未知 format、无效哈希、字段类型错误及超限内容。清单上限 64 KiB，脚本沿用现有 8 MiB 上限，下载只访问所选后端的上述哈希路径，不把 path 当下载 URL。

清单 GET 返回 200 和稳定的 `ETag: "<planId>"`，条件匹配返回 304；无发布为 404，已发布数据损坏为 503，错误统一为 `{ "error": "<稳定错误码>" }`。清单允许缓存但必须重新验证；哈希脚本为不可变资源。新接口沿用现有公开推荐下载的访问策略，管理操作沿用现有管理员鉴权及请求来源策略。

健康摘要使用 `GET /lx/recommendation-status`，200 返回 `{format, planId, enabled, paused, platforms}`。各平台包含 targetSha256、最近完整检查时间、P/N/V/F/E/U 与不支持计数、decisionReason、health 及独立 stale 标志；health 为 available/degraded/limited/unavailable。没有清单时 planId 为空、平台 unavailable。状态只公开脱敏摘要，不包含签名 URL、脚本凭证或原始异常堆栈；客户端只展示与当前目标哈希相符的健康摘要。仅健康时间变化不增加 planId，不下载或重启脚本。目标映射、脚本版本或音质变更才创建新清单。

QQ、网易可独立产生推荐，targets 允许缺少尚无足够证据的平台。缺失平台明确表示暂未提供，不得自动跨平台找同曲。已有目标仅因新一轮检测失败而保留并标注状态，不通过删除映射来强制清除客户端本地版本。

例外是管理员回退到尚未包含某平台的历史清单：有效 200 清单明确缺失该平台时，客户端停止为它创建新解析，保留已有播放及请求租约，设置页显示暂未提供；本地脚本文件可保留用于恢复。该行为与 404/损坏响应保留本地有效映射严格区分。

### 5.2 发布事务与历史

先校验输入版本并归档全部脚本，再保存不可变清单与决策记录，最后原子替换 `automatic/state.json`。该文件同时包含 currentPlanId、previousPlanId、paused、单调递增 controlRevision 及当前 decisionId，作为唯一提交点；不能分别改写暂停文件和 current 指针。不可变文件先落盘，state 使用现有原子写入能力，失败仍指向旧清单，未引用的准备文件稍后清理。决策链接上一条已提交记录，历史只沿已提交链读取，不能把提交前中止遗留的文件展示为已发布。

使用发布锁、expectedPlanId 和 controlRevision 防止管理操作与自动任务覆盖彼此；在锁内复核总开关、暂停状态、控制 revision 和参与输入版本。两个平台分别完成决策时，基于锁内最新清单合并未改平台；CAS 冲突时重新核对证据，不能拿旧快照覆盖另一平台。管理员在检测或发布准备期间暂停，旧任务不得在暂停后继续发布。回退创建新清单，并在同一次 state 提交中切换指针、置 paused、递增 revision；断电不能出现“已回退但未暂停”的中间状态。

决策保存 policy 版本及配置指纹、样例/检测器版本、参与脚本哈希、各确认轮报告 ID、逐曲增益/退步集合、每平台计数、旧/新目标及理由。自动发布使用明确的 system actor，不能伪造管理员 ID；旧发布结构要求 PublishedBy>0，不能直接塞入自动记录。

自动状态与清单放入 `<runtime_directory>/source-recommendations/automatic/`，复用脚本归档。决策常规保留上限 100 条/30 天；当前和上一版可回退清单、对应决策及脚本不受该期限清除，确认中的派生逐曲证据也独立保存。保留输入版本、时间和报告 ID，原始报告清理后不能丢失作出决策的依据；历史界面明确标注原报告已过期。

备份在发布锁下取得一致引用集，显式包含 automatic 子目录及全部被保留清单引用的脚本。恢复后保留当前清单，重置未完成任务并重新安排巡检。

现有 Store.Backup 在“未发布旧版全局推荐”时提前返回，必须调整为分别收集旧版与自动数据；只使用自动推荐的安装也必须能完整备份。旧版 Store.prune 和新增自动清理必须在同一归档维护锁下，使用旧版历史、自动当前/上一版/保留历史及准备中事务的联合引用集。不能只修自动清理：旧版一次手动发布触发的 prune 也不得删除自动清单的脚本。锁内只进行短时文件操作，不包含脚本网络检测。

### 5.3 管理接口

| 接口 | 语义 |
| --- | --- |
| `GET /admin/source-recommendations/automatic` | 当前 state、平台健康、调度进度、候选及确认理由 |
| `GET /admin/source-recommendations/automatic/history` | 保留的清单与决策，按时间倒序，上限 100 项 |
| `POST /admin/source-recommendations/automatic/control` | `{expectedPlanId, expectedControlRevision, paused}`，返回提交后的 state |
| `POST /admin/source-recommendations/automatic/check` | `{expectedPlanId, expectedControlRevision}`，请求立即巡检当前及待确认候选；无当前目标时安排首次扫描 |
| `POST /admin/source-recommendations/automatic/rollback` | `{expectedPlanId, expectedControlRevision, fromPlanId}`，只接受保留历史，返回新清单及 paused state |

GET/控制/回退成功为 200；立即巡检接受为 202，返回调度标识，已有同一请求则返回相同标识。CAS 不符或检测器忙为 409，输入无效为 400，历史不存在为 404，总开关关闭或当前暂停时请求启动自动检查为 409 并说明原因。启用但尚未发布时 expectedPlanId 使用空串。控制和回退更新 controlRevision，普通巡检不更新；控制类变更使旧自动任务失效，重试不得绕过 CAS。

### 5.4 老客户端与老服务

- 现有 `/lx/recommendation` 与 `推荐/recommended.js` 继续提供管理员发布的单脚本；新自动计划不覆盖该入口。
- 老客户端继续使用原协议；它们不会获得按平台自动路由能力，不能声称只升级后端就完成此功能。
- 自动模式要求新接口；接口未实现/尚未发布且本地无可用自动目标时，明确提示并保留原选择。旧的单脚本推荐仍提供独立入口，不在自动模式下静默切换到人工维护的旧协议。
- 自动模式已有本地目标时，404、临时 5xx、网络错误和清单损坏都保留本地版本并显示更新异常；客户端不得凭一次响应清空已有目标。
- 管理页面将全局旧推荐放入“旧版客户端推荐”区域，避免与自动平台推荐混淆。

## 6. 客户端实现与缓存边界

### 6.1 设置与自动更新

新增“自动推荐（标准音质）”选项，显示 QQ、网易各自正在使用的脚本、本机计划版本、后台最新版本及健康状态。此模式明确使用标准音质；手动脚本模式继续沿用原有音质选项。

升级不修改普通源、导入源或 Navidrome 用户的选择。现有单脚本推荐用户仍使用原模式，主动选择一次新模式后开始跟随；以后不需要手动发布或更新。

配置保留现有 `type: lxmusic`，新增 `catalogKind: automatic_recommendation` 和独立 isAutomaticRecommendation 判别，使用独立稳定 ID 及 backendOrigin；不伪造一个拼接脚本或借用旧版 `推荐/recommended.js` 身份。选源、设置列表、导入导出和启动恢复分别识别此类型，不能被旧版 isRecommendation 分支拉回单脚本接口。各平台脚本与实际应用记录由路由组件保存。

应用启动和前台运行期间每十五分钟检查一次清单，使用 ETag，回到前台时只在到期后检查。系统挂起时不承诺定时运行，也不新增移动端后台服务。离线或更新失败使用本地已应用的目标；初次选择至少有一个平台准备成功才允许启用，另一个平台未就绪须明确显示；两个平台都不可用时保留原选择。

轮询为单飞任务，启动、计时器和前台恢复不能并发创建更新。304 只表示远端 desired 清单未变，仍须处理本机 desired 与 applied 不一致的平台及重试失败的准备；状态摘要独立刷新。每次检查每平台最多准备一次，失败采用一分钟起、上限十五分钟的退避；上下文名额释放后可在退避到期重试，不进行无界紧循环。只有已持久化对应完整清单时才发送其 ETag；本地清单丢失或损坏时强制取 200。

已有本地版本时沿用启动恢复预算，不等待远程下载完成才启动播放。后台取得的新版本按后续解析更新规则应用，不能让多脚本下载和准备延长现有启动等待。

### 6.2 请求固定身份与运行时

新增推荐路由组件，根据歌曲原平台取得 target；始终使用原歌曲 ID 和元数据。每次解析固定：后端 origin、平台、128k、脚本哈希及元数据快照。planId 用于追踪，但另一平台单独更新不能使本平台解析身份变化。

在同一后端 origin 和当前自动选择会话内按脚本哈希复用独立 QuickJS 上下文，同一脚本被两平台采用时复用一个上下文。跨服务器或切出再进入自动模式时不能直接复用旧会话。不能通过调用普通“选择音源”接口来完成每次平台路由。

服务器清单须整体校验合法，再按平台独立下载、校验并准备目标。QQ 准备成功即可应用 QQ；网易失败则保留本机网易目标，不得让一个平台阻塞另一个平台。持久化区分 desiredPlanId 与各平台实际应用的 planId/哈希，界面不能把尚未应用的版本显示为已使用。

准备成功要求该运行时完成初始化并声明支持对应平台及 128k，仅“存在任意 sources”不够。未获推荐的平台直接提示当前自动模式暂不支持该平台，不把网易歌曲交给 QQ 目标，也不静默改用普通源。

脚本先按哈希保存不可变文件，再用一个原子有效映射记录提交已准备成功的平台目标，最后发布内存路由；失败保持之前记录，重启按持久化映射恢复并验证内容。最终提交复用选源操作的串行边界，网络下载和初始化放在边界外。此处只能复用“独立准备”的思路，不能直接调用现有 `_RuntimeCandidate.commit()`，它会立即销毁旧活动上下文。

所有异步更新捕获选择 epoch、模式和 backend revision，下载、初始化和最终提交时检查，同时核对该平台的待提交哈希仍等于最新 desired 目标。另一平台变更不作废本平台相同哈希的准备；同一会话中已被新目标替代的旧候选不得晚到覆盖。用户改选普通音源、切换服务器或退出后，停止轮询并作废旧候选；晚到的任务不得改写新选择或重新启用自动模式。

已有解析持有原上下文租约，新清单只影响之后开始的解析。原请求结束再释放旧上下文；取消只作用于对应请求，不销毁其他平台的执行环境。最多保留四个上下文（活动、候选及待释放旧实例合计）；超出时延迟应用新清单，不强杀旧请求或持续增建实例。

清单变化不能增加全局 lxSourceRevision 后触发当前歌曲重载。自动模式中，MusicService 和 PlaybackService 使用请求自己的 target 身份做复用与结果校验；用户真正切换选源模式仍沿用现有取消流程。

### 6.3 音质必须贯通

在 AudioQualityService 集中定义自动模式的有效音质：应用内为 standard、脚本参数为 128k。effectiveQualityFor、requestQualityFor 和能力查询使用当前平台路由，不能继续读取普通模式的单例运行时声明。播放、预加载、音频下载和缓存读写都沿用这一有效音质；不能请求 128k 却把文件标记或缓存为 FLAC。保留用户手动模式的首选音质，退出自动模式后恢复原有选择，不修改全局首选设置。

### 6.4 缓存

- 已解析 URL 和待完成解析的复用键，纳入 origin、平台、音质、目标脚本哈希及现有元数据身份；只健康信息变化时保持键不变。
- QQ 目标更新不清理网易有效 URL；旧目标正在进行的结果只能回到持有该身份的原请求，不能写入新目标的缓存。
- 推荐脚本、服务器清单及各平台实际应用记录使用新的缓存，不能复用当前仅保存一个 pending 脚本的键；按实际后端 origin 隔离。清单新版本到达时，在本机仍使用的旧目标不能被缓存清理提前删除。
- 已完整缓存的音频仍以原平台歌曲身份复用，继续执行现有完整性与短音频保护；切换脚本不会批量删除音频文件、歌词或用户歌单。
- 签名播放 URL 不进入推荐清单和自动决策历史。

## 7. 管理界面

首页置顶显示 QQ、网易两张推荐卡：当前脚本、自动模式、P/N、V、限制/未验证数量、最近巡检、下次检查及本次保持/替换理由。结构可识别与实际播放成功的措辞保持区分。

提供“暂停/恢复自动维护”“立即巡检”“查看决策历史”和“回退上版并暂停”。回退创建指向上版目标的新清单，保留完整历史并阻止旧自动任务覆盖。暂停后保留当前推荐及脚本下载能力，不中断客户端。首版不增加逐平台人工固定、权重编辑或依赖图；部署总开关关闭时显示一次性配置说明。

报告增加按测试歌曲横向汇总及“多个脚本共同失败”提示。对同主机失败只展示相关性，不直接断言同一后端实现；首版不建设自动依赖图，也不自动更换测试歌曲。

## 8. 实施顺序和验收

| 步骤 | 交付 | 必须通过的验收 |
| --- | --- | --- |
| A：证据评估 | 纯评估函数、有版本 policy、按歌曲汇总 | 无固定通过率线；正面覆盖有增无损才替换；U→P 明确记为证据增加；E 不制造优势；互有胜负保持；共同失败不否决；疑似短资源/可疑重复不计 P；时长未知不计 V；先筛后排不会遗漏合格候选；跨轮至少一首持续增益 |
| B：后端闭环 | 定向检测、调度、多轮确认、原子发布、管理状态、备份 | 模拟时间自动替换，无需页面点击；输入变化/证据过期清零；任务互斥且大样例分组可完成；归档旧源可巡检；暂停/回退期间旧任务不发布；并行平台决策不覆盖；回退与暂停同一提交点；旧版未发布仍备份自动数据；旧版 prune 不误删自动脚本 |
| C：客户端接入 | 新选项、清单更新、按平台路由、请求身份与缓存适配 | 混合歌单选对脚本；一平台准备失败不挡另一平台更新；304 重试未应用目标；同会话旧候选晚到不覆盖；旧解析租约有效；选源/服务器改变作废更新；重启恢复部分应用；音质/能力/缓存一致；手动首选音质保留；旧入口独立 |
| D：整体验收 | 两端集成与 NAS/Windows 验收 | 自动发现故障、复核、发布、客户端自动采用的完整链路；资源预算、任务回收、备份恢复与普通播放回归通过 |

自动闭环的主要验收使用可控脚本与 HTTP 服务，模拟 A 正常→持续失败、B 持续正常、共同样例失败、DNS/策略限制及发布中断；不能依赖公网音源恰好正常来证明规则正确。

必须另外覆盖：首轮后重启且证据过期；确认各轮增益歌曲不同；QQ 发布后网易持有旧清单准备提交；清单 200 后网易准备失败、下一轮 304 后成功；同一会话更换两次目标且旧下载最后完成；脚本只声明 QQ 或不支持 128k；用户首选 FLAC 时进入/退出自动模式；旧版发布触发清理及只自动模式的备份恢复；四个上下文已占满时延迟应用且最终回收。对进程在提交前后被中止做恢复验证，不能只测正常返回。

真实环境另外检查实际公网响应、CPU/内存、批次耗时及 Windows 播放表现。首版不要求扩建测试平台，不把每个失败源都查透才开始开发。

发布时先部署兼容后端但保持自动功能未启用，再发布适配客户端；启用后系统自行完成首轮扫描与确认。确定性集成测试覆盖自动发布；NAS 实际启用后的首轮只做一次上线验收，后续决策不增加人工批准步骤。

## 9. 完成标准与明确边界

完成标准：用户选一次自动推荐；后台发现某平台有满足最小证据量、保留已有正面覆盖且持续增加检查覆盖或可验证证据的候选时，自动完成复核与发布；客户端在下一次清单检查并成功准备后自动使用该平台的新脚本，不打断当前播放。管理员可以解释每次变更发生的原因。

本方案解决渠道级持续故障和覆盖差异。若某首歌所有候选都无法取得地址，按平台推荐不能创造可用资源；单曲即时备用、自定义检测代理、自动样例生成、实际解码与客户端反馈均留作后续独立需求，不影响首版闭环交付。

- 管理页面提供平台状态、确认轮次、当前批次进度、完成任务和资源读取量、暂停/恢复、立即巡检及历史回退。任务与字节累计来自已收尾的报告，不含脚本接口流量；异常退出可能导致尚未记账的最后一批未计入累计。
- 自动与旧版推荐共用受引用保护的脚本归档；仅自动模式、甚至首次发布前的暂停状态也纳入备份。
- 客户端 `automatic_recommendation_router.dart` 负责清单、不可变脚本和有效映射。各平台独立准备与应用，304 继续重试未应用目标，离线启动恢复已保存版本。
- 自动选源使用现有配置事务；失败恢复原选择，后续目标更新不增加全局选源 revision。QuickJS 按哈希复用，最多四个上下文，旧解析以租约保护，释放后清理旧脚本。完整音频缓存继续使用原歌曲身份，临时 URL 使用平台和脚本哈希隔离。
- 自动模式有效音质固定 standard/128k，普通首选设置不修改。普通模式、旧版推荐与自动推荐分别处理；自动配置不开放脚本编辑入口。

### 启用方式

后端配置合并以下两项即可使用默认周期与证据参数；不需要启用 admin：

```yaml
source_recommendation:
  enabled: true
  automatic:
    enabled: true
```

默认全量 72 小时、巡检 3 小时、至少 3 首样例和 2 首正面证据、2 轮确认、证据有效期 6 小时。完整配置与运维说明见后端 `docs/15-automatic-source-recommendations.md`。部署适配客户端后，在音源设置选择一次“自动推荐（标准音质）”；后台未完成首次确认时，客户端明确提示尚未提供目标，并保留原有选择。
