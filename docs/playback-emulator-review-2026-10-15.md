# 模拟器播放复测（2026-10-15）

## 条件与证据

使用已安装的 Android 调试 APK、现有账号和 HYWmusic 公益版音源。
QQ 和网易各选三首歌曲。绕过完整文件缓存，检查原生 ready/playing、
最终目标歌曲、进度推进、pending 和原生操作是否收尾；不以这些状态代替听感验收。

诊断数据位于忽略的 build 目录：

- `playback-extra-r1-{verification,events}.jsonl`：常规切歌、暂停恢复、快速选择、EQ、自动下一首。
- `playback-extra-r2-{verification,events}.jsonl`：修正诊断取样方式，增加连续十次选择、45 秒 seek、后台 15 秒及返回。
- `playback-extra-r3-uncached-{verification,events}.jsonl`：临时禁用原生流缓存的网络对照；结束后恢复缓存预算。
- `native-playback-fixture-results.jsonl`：独立预缓冲、403、429、失败恢复、缓存和取消的可控测试。

第一轮诊断每次取样使用 VM `getInstances` 扫描堆，可能引入 GC/暂停，
不适合据此计算日常性能或失败率。后续改为从 PlaybackService → EngineHost
直接读取当前引擎，不再扫描堆。第一轮失败保留，不能因重试成功而抹去，
也不能未经独立复现就全部归因于线上音源或播放器。

## 已确认的缺口

### 导航失败可能没有错误提示（优先处理）

第一轮 QQ 预备接管在 `prepared_adopt` 超时，随后出现 state=error、
pending 为空、errorMessage 为空。再次播放能够恢复，没有永久锁住。

源码中 `_runNavigationTransition` 的预备激活失败/预算耗尽路径会生成
`PlaybackTransitionResult.message`，但 `_finishFailedNavigation` 在无法保留
当前播放的分支只设置错误状态和清理 pending，没有用该消息兜底。
全屏播放器的错误横幅直接使用 errorMessage，因此这个终态缺口需要修正。
修复应保留当前事务的实际失败原因，只在消息缺失时兜底；旧事务不得覆盖新事务。

### 预备命中统计失真（已由源码确认）

`TrackSwitchTiming.preparedEngineHit` 和 `preparedActivationMs` 初始化后
没有在预备成功路径赋值。实际日志有 `audio_engine.prepared_slot_activated`，
但业务统计仍打印“未命中”和 0 毫秒。应从成功提交的同一事务记录实际激活耗时，
避免重复统计和迟到事务污染。修正前以原生操作/激活事件为准。

### 预备接管耗时仍值得优化（原因尚未完全定位）

第二轮六次成功的预备接管耗时分别为 1751、1781、3061、1012、895、1208 ms。
预缓冲启动、实际缓冲完成、接管后 ready 是三个不同节点，不能把“已发起预加载”
当作“能够立即出声”。后续应给三个节点增加同一 source/generation 标识，
区分还在下载、缓存读取、格式探测/解码器准备和 Dart/原生桥接等待。
不建议仅凭总耗时加长超时或更换引擎。

## 超时记录的解释

第一轮有三次原生阶段超时：QQ 首次 load_source 剩余约 5.6 秒、
QQ prepared_adopt 约 8 秒、网易首次 load_source 剩余约 4.7 秒。
首播对应解析已成功，因此这三次不能称为“获取播放链接失败”。
解析与原生装载共用总预算，前序耗时会减少装载时间；不能脱离总预算直接增加各段超时。
第一轮存在堆扫描干扰，实际发生频率需要用后续低干扰数据或实机复核。

第二轮 34 个状态观察点未出现错误终态或进度停止，两个平台的十次快速选择均
落在最后目标；后台 15 秒均推进约 15 秒，返回后继续正常。没有复现永久 loading。

第三轮禁用流缓存的 26 个观察点也未出现错误终态、pending 残留或进度停止。
原生日志确认本轮 `cache=false`。六次预备接管为 1732、1030、3276、2143、
1916、4734 ms；普通源装载为 3879、2062、2915、2169、2888、3498 ms。
这说明无缓存路径可用，但预备接管的尾部耗时仍需拆解，不能宣称已经秒切。
第二轮和第三轮的成功不代表第一轮的错误提示缺失可以忽略。

本轮只调整诊断脚本与补充记录，没有修改业务播放逻辑。

可控故障测试结果：坏的下一首返回 403 时当前曲保持 ready/playing 并正常结束；
主动激活坏源后错误包含 HTTP 403，随后装载正常源可恢复。预备源交接 542 ms；
缓存再次装载 551 ms 且无新增请求；模拟上游离线仍能读取已缓存的 WAV；
关闭缓存会新增一次请求；慢请求超时后 dispose 29 ms。
HTTP 429 在装载异常和 errorStream 两条路径均保留状态码，服务端只收到一次请求。
这些是可控 WAV 测试结果，不能替代第三方 CDN 或实机听感验收。

## 后续修复与复验

已补齐导航失败的消息和恢复操作兜底：优先保留当前事务的实际问题与操作限制，
其次使用导航结果消息，最后使用通用错误提示。终态清理 pending，旧请求不得覆盖
新请求；未支持格式等已分类错误不被替换成通用可重试错误。

预备激活现在等待实际成功后再提交展示和统计，早到的原生 source-commit 事件
不再抢先发布成功。过期激活返回无论成功还是失败均不能覆盖新选择。
计时记录实际 activation/set-source，原生 MediaItem 与 Dart AudioSource 使用
相同的不透明 UUID，关联预缓冲完成、源复用与装载事件，不记录 URL/鉴权。

验证结果：362 个普通 Dart 测试和 6 个真实 QuickJS 测试通过，9 个原生 JVM
测试通过，flutter analyze 无问题，debug APK 构建并安装成功。新增回归覆盖
激活超时消息/重试、实际格式错误保留、早到和重复提交、过期激活成功/失败隔离。

新版 APK 的低干扰 QQ/网易复验产生 27 个观察点（QQ 14，网易 13）。
首播 QQ 复现一次 load_source 超时：该阶段预算 5912 ms、记录等待 5944 ms，
此时 URL 已解析成功。终态正确显示“播放器操作超时，请重试播放”，pending
为空，随后同曲重试恢复。其余观察点的手动下一首、快速三次选择、暂停恢复、
EQ 切换和自动下一首均符合目标，playing 样本的播放进度持续推进。

六次成功接管的业务 activation_ms 为 6152、5293、3925、2852、2181、2655 ms，
prepared_engine_hit 均为 true，与引擎激活日志对应；未见同代次重复成功统计。
原生日志的 source_adopted 与 Dart source_id 对应，且有源在接管之后才记录
preload_buffered。这证明“已复用预备源”并不等于“切歌前已缓冲完成”。
当前结果确认了失败恢复和统计修复，也确认数秒接管与偶发原生装载超时仍存在，
不能宣称已经秒切。该轮调试采样耗时不是声学起播延迟，模拟器也不证明实际听感。

同包再次运行可控原生故障测试：预备 WAV 接管 296 ms；坏预加载时当前曲保持
ready/playing，正常完成；主动坏源保留 403，随后正常源恢复。缓存热加载
335 ms、无新增请求，模拟上游离线仍 ready；禁用缓存新增一次请求。
慢请求取消后 dispose 67 ms；429 在 load/errorStream 中均保留，仅一次请求。

## 预加载延迟的定位与策略修正

原来的目标控制条件为 `STATE_READY && !isLoading()`。ready 只表示可播，
并不意味着当前源停止补缓冲。可控慢流测试中，当前曲正常播放并已有数秒缓冲，
下一首虽然提前 5 秒提交，却直到切歌才开始 HTTP 请求，接管 2161 ms。
同端点当前曲已补完缓冲时，下一首可提前请求，接管 220 ms。
下一首固定延迟 1800 ms，禁用流缓存，因而不是磁盘缓存命中造成的差异。

核对 Media3 1.9.2 源码：共享 DefaultLoadControl 的 shouldContinuePreloading
已在当前播放器需要数据时让后台加载避让；而 DefaultPreloadManager 对
NOT_PRELOADED 调用 clear，可能丢失已预载的采样。原来按 loading 状态动态切换
目标并 invalidate 是重复且有破坏性的调度。

修正为稳定的 2 秒目标，交由共享 LoadControl 调度，不再在当前曲补缓冲/seek
时切换到 NOT_PRELOADED。仍由 Dart 提交和取消候选，保持单项当前播放列表、
同源对象接管和既有事务/超时。没有扩大缓存、延长超时或增加播放器实例。

新增 native 日志记录 preload_requested、source_adopted 的 buffered 标记，
以及单调时钟测量的 source_ready/audio_advancing。原生 load_source 慢与
Dart 到原生的等待可以分开检查。上轮 6152 ms 接管中，prepared_adopt 占
6029 ms，启动确认仅几十毫秒，因而不能把主因归到 _waitForStartup。

修正后的受控测试结果：

| 场景 | 第一次 | 可复跑脚本复验 | 下一首 HTTP 请求数 |
| --- | ---: | ---: | ---: |
| 当前曲仍持续加载，提前预备下一首 | 166 ms | 603 ms | 1 |
| 当前曲已补完缓冲 | 213 ms | 136 ms | 1 |
| 下一首预备完成后拖动当前曲 | 258 ms | 99 ms | 1 |
| 不预加载的普通装载对照 | 2073 ms | 2086 ms | 1 |

脚本 `tool/verify_android_preload.cjs` 使用本地 WAV 慢流和 1800 ms 响应延迟，
验证 ready/playing、任务结束和下一首只请求一次，运行后恢复缓存设置。
以上是受控延迟，不等同于实机声学延迟，也不能推导所有 CDN 都会达到该速度。

真实 QQ/网易再跑一轮 26 个观察点，无错误终态、残留 pending、错误歌曲或
playing 样本进度停止。QQ 三次预加载业务接管 946、1474、1623 ms；
网易为 4324、3886、2470 ms。QQ 前两次切歌前已经预缓冲完成，原生接管到
ready 为 579、1075 ms。网易两次手动切换在预缓冲尚未完成时接管，仍需等待。
其中一次业务接管 4324 ms，原生实际装载为 1005 ms，还包含宿主队列与
Dart/原生调用间等待；不能把全部业务耗时归为 CDN 下载或解码。

故障隔离回归：坏预加载不影响当前曲，当前曲正常完成，403 后可恢复，429
只请求一次且保留状态；热缓存零新增请求、离线缓存可用、禁用缓存会发请求。
该轮缓冲 WAV 接管 203 ms、热缓存 494 ms、慢请求取消后 dispose 30 ms。
debug APK 构建和 9 个原生 JVM 测试通过；本轮生产改动限于原生预加载策略和日志。

另做一轮不在切歌期间轮询 VM 的真实流验证：两平台各连续切换两首，每首间隔
7 秒，业务接管分别为 QQ 1438、1226 ms，网易 1485、1095 ms，四次切歌后的
进度验证均通过。原生 set-source 为 1434、1225、1481、1091 ms，启动确认
仅 2、0、1、2 ms。该轮样本没有显示 _waitForStartup 造成显著等待。
与轮询轮相比，预备时机和缓存状态也会变化，因此不能把所有差值都归因于调试。

可复跑脚本增加激活前 HTTP 标记，断言三种预加载场景的下一首请求早于激活，
普通装载对照晚于激活，避免仅测最终 ready 而漏掉“预加载根本没有起请求”的退化。

## 预备源替换与追加跳转对照

在同一个已安装 debug APK、同一模拟器上运行两条现有 API 路径，没有修改生产
播放器代码。替换路径为 `setAudioSource(next)`；追加路径为
`addAudioSource(next)`、`seek(index: 1)`、ready 后移除旧项。两条路径复用
同一个播放器，配置相同。追加路径借鉴 Q-music 的列表操作方式，但不代表运行
了完整 Q-music 客户端，也没有复制它解析前 stop、占位音源、缓冲参数等行为。

新增 `tool/compare_android_source_switch.cjs`：关闭流缓存，以同一份 120 秒 WAV
作为输入，下一首固定延迟 1800 ms；播放器静音，运行后恢复流缓存预算。
预备组提前 4 秒向同一个 DefaultPreloadManager 提交下一首，原生日志确认全部
六次均完成 2 秒预缓冲并接管原音源。非预备组不做预加载。两种状态、两条路径
各重复三次，交替执行顺序；所有下一首只发出一次 HTTP 请求。测量从切换前
HTTP 标记完成后的同一个 Dart Stopwatch 开始，等待正确目标 ready，而不是
只统计原生跳转命令提交时间。

| 状态 / 路径 | 三次 ready 耗时（ms） | ready 中位数（ms） | 进度推进中位数（ms） |
| --- | --- | ---: | ---: |
| 已预缓冲 / 替换 | 146、140、115 | 140 | 279 |
| 已预缓冲 / 追加跳转 | 183、200、185 | 185 | 317 |
| 无预缓冲 / 替换 | 2053、2035、1992 | 2035 | 2210 |
| 无预缓冲 / 追加跳转 | 2026、2108、2054 | 2054 | 2217 |

进度推进指标为 ready 后 Dart 播放位置增加超过 100 ms 的观察时间，包含该
观察窗口，不是实际出声延迟。原生 audio_advancing 日志也出现于全部十二个
目标 source_id；两条路径最终目标一致、ready/playing、仅保留一个列表项。

另外验证两条路径的预加载 403 隔离、激活失败后正常源恢复：当前曲未被坏
预加载中断，激活后分别 92 ms / 86 ms 返回 PlayerException，无重复坏源
请求，随后恢复 ready/playing 且进度推进。每条路径又连续复用播放器切换三次，
覆盖播放中切换、暂停后切换保持暂停、再次切换并恢复播放，六次目标/列表数量/
播放意图检查均通过。计时测试和恢复测试分别落在 build/ 下的
`source-switch-comparison.jsonl`、`source-switch-robustness.jsonl` 及对应 native 日志。

结论限于此受控 WAV 对照：没有观察到追加跳转降低接管耗时，不能据此替换正式
实现。它也不能证明真实 QQ/网易压缩音频、硬件设备或整个 Q-music 客户端的耗时
相同。当前实验排除了“仅更换列表操作必然显著更快”的假设；真实流仍需按
预缓冲完成状态、调用排队和原生装载阶段继续归因。

## 同链接真实 QQ / 网易流对照

新增 `tool/compare_android_real_stream_switch.cjs`，使用同一个 debug APK、模拟器、
现有 Media3 配置。每首只调用一次现有 MusicService 解析，所得 URL/请求头保留
在 VM 内存；替换和追加路径复用同一资产。报告只保留 URL SHA-256，不输出签名
链接。配置音质为 128k，绕过完整文件播放路径、禁用原生流缓存，最后恢复缓存
预算。全部十二对的 URL 指纹和音质相同。

最初选取 QQ 三首（Forever Love、献给永远的、遗书）及网易三首
（PIMMIE'S DILEMMA、Alive、Die For You）。QQ 三首均解析成功，分别耗时
3276/1621/1305 ms；网易第一首 2675114848 在 1580 ms 后返回空结果，没有进入
音频计时组，保留失败记录；另两首在 1853/2079 ms 后解析成功。此轮不把空结果
推断为超时，也不分析该曲失败根因。音频切换耗时从解析完成之后测量，不含这些
解析时间。网易实际使用两首，QQ 使用三首轮换。

每平台三轮，每轮包括预加载/不预加载、替换/追加，共 24 次切换，交替两条
路径先后顺序。每次使用一个新的静音播放器实例，先播放当前真实流，再切下一首；
每个实例内部复用播放器，两条路径不销毁重建播放器来切歌。预加载组提前 6 秒
提交候选，原生 source_adopted 确认十二次全部 preload_buffered=true。
这是切换原语的受控对照，没有调用业务 EngineHost/UI，也不是运行 Q-music。

| 平台 / 状态 | 替换 ready 中位数（ms） | 追加 ready 中位数（ms） | 替换原生音频推进中位数（ms） | 追加原生音频推进中位数（ms） |
| --- | ---: | ---: | ---: | ---: |
| QQ / 已预缓冲 | 523 | 376 | 665 | 587 |
| 网易 / 已预缓冲 | 537 | 280 | 748 | 473 |
| QQ / 无预缓冲 | 1923 | 1827 | 2093 | 1890 |
| 网易 / 无预缓冲 | 1054 | 840 | 1207 | 1036 |

原生音频推进取日志中的目标 source_id 的 onAudioPositionAdvancing 回调时间，
与 Dart 同设备 DateTime.now 记录的切换起点按 epoch 对齐；不使用追加命令返回
时间代替起播。该指标仍不是声学测量，可能包含回调派发时间。

预缓冲组 ready 的三次原始值：QQ 替换 637/523/331 ms、追加 376/297/477 ms；
网易替换 537/536/539 ms、追加 767/280/156 ms。追加在六对中四次较快、两次
较慢；同样目标流也有反转，不能把小样本中位数视为稳定收益。未预缓冲组也有
追加 2163 ms、替换 1166 ms 的反例；真实上游连接状态不是本地固定延迟端点，
不能将该组差值全部归因于列表操作。

全部 24 次均 ready/playing、目标对象匹配、出现原生音频推进、清理后 index=0
且列表项数为 1，无播放器异常或超时。没有验证全业务 UI、快速并发意图或实机
声学效果，因此不是正式切换方案的完整回归验收。证据保存为 build/ 下的
`real-stream-switch-comparison.jsonl`、`real-stream-switch-comparison-native.log`。

本轮结论：真实流中追加路径有百毫秒量级的改善迹象，值得作为局部优化候选；
但没有稳定胜出，不能据此直接迁移生产播放架构。预缓冲是否完成带来的差异
更大；单纯取得 URL 仍可能有约 1～2 秒以上音频装载，不能与脚本解析混为一谈。
保留正式替换路径，先针对真实业务中预缓冲完成率和剩余装载/调用等待进一步
定位，再决定是否引入原生追加快路径。本轮仅增加实验脚本和记录，无生产代码修改。

## 两轮推进：业务分段诊断与追加路径试验

第一轮在 PlaybackService/EngineHost 增加分段日志，关联排队、解析、计划准备、
原生源装载及就绪耗时。预取日志另外记录定时计划、取消、实际触发与 URL 计划
完成；URL 就绪仍不代表原生音频已缓冲。未改变预取延迟或自动导航策略。

新增 `tool/verify_business_playback_switch.cjs`，走实际 PlaybackService，
绕过完整文件并关闭原生缓存，QQ 三首、网易两首轮换。场景包括首次点播、
一秒后下一首、等待预取后下一首、进度推进、自然结束、连续点选、暂停恢复。
静音运行；日志保留在 VM 内存中，测量期间不反复经 VM 拉取状态，最后统一导出。
结束后恢复队列、模式、音量、缓存预算和实验开关，但不恢复正在播放。

诊断证据：首轮 EngineHost 源操作排队为 0～14 ms，没有证据表明这批样本由
原生操作队列堵塞主导。一秒后切歌早于现有 2.5 秒预取定时触发，因此走冷解析；
仍有约 1.3～2.8 秒解析和约 1.9～3 秒以上装载。一次 QQ 接管时原生缓冲尚未
完成，接管后约 11 ms 才收到完成日志；不能把预备槽位命中当作缓冲完成。
当时也观察到同一播放代次多次取消/重设预取计时；后续修复与验证见本文末尾。

第二轮实现受实验开关保护的追加/跳转/移除旧项。后台预取仍使用隔离的
DefaultPreloadManager，只有正式切歌时临时出现两项。保持既有纪元、事务、
队列及播放意图校验；仅对单项且 ready 的播放器使用追加，completed/idle
保留替换。失败时清理局部列表，必要时丢弃播放器并由下一次请求懒重建。
补充独立错误流监听，处理原生 seek 已报 HTTP 错误但 Future 未完成的情形；
错误竞争在既有总预算内，不为每一步重置超时。默认仍关闭追加实验。

完整业务三轮中的预缓冲手动下一首（用户操作开始至业务 playing，ms）：

| 平台 | 替换基线 r2 | 追加 r1 | 追加 r2 |
| --- | ---: | ---: | ---: |
| QQ | 2254 | 2118 | 2154 |
| 网易 | 1849 | 1163 | 1866 |

这几组不是同 URL、同连接状态的配对实验，不把差值全归因于追加操作。追加组
首次及冷切歌仍可能超过数秒，两次连续快速点选也没有稳定改善；自然结束后
播放器为 completed，仍走替换，不能把该场景算作追加收益。上述两轮追加业务
场景均结束于正确目标、pending 清空、无残留错误，进度推进，暂停/恢复成功。
首次基线脚本曾调用不存在的 play()，为脚本错误；改为 resume() 后以 r2 为准。

证据文件为 build/ 下 `business-switch-baseline-r2-*`、
`business-switch-append-r1-*`、`business-switch-append-r2-*`。暂不将追加设为
默认，也不声称解决了全部数秒装载。已预缓冲业务切换剩余约 1～2 秒等待仍
需定位，不能从独立实验耗时简单相减后认定为某一层的浪费。

补充验收：QQ/网易混合队列的首次、快速下一首、预备接管、自动下一首、
连续点选及暂停/恢复通过；临近结束时手动点选后再观察一秒，最终目标没有
被旧完成事件覆盖。见 `business-switch-append-mixed-*`。

受控 HTTP 403 经实际 JustAudioEngine 追加路径验证，406 ms 内按
accessDenied 结束，释放部分追加后的播放器，未重复请求坏链接；随后正常
链接恢复播放且进度推进，暂停后追加仍保持暂停、列表单项。见
`engine-append-failure-recovery.jsonl` 及对应原生日志。该受控故障验证引擎，
不冒充完整业务的第三方接口故障验收。

新增五项引擎回归覆盖预备追加保持暂停、错误流报错但 seek 不返回、旧项移除
失败、连续冷源切换单项一致性、追加超时后的迟到完成隔离。最终普通测试
367 项通过，6 项需显式启用的真实 QuickJS 测试默认跳过；静态检查无问题。

## 原生重复 stop 的历史实验及同链接对照（已撤回）

进一步核查发现 Dart 层虽然已去掉额外 stop，Android 插件 load() 仍在
setMediaSources 前调用 player.stop()。Media3 1.9.2 的 stopInternal 会禁用
renderer、释放源列表，并在非 foregroundMode 时 reset renderer；而
setMediaItemsInternal 本来就支持直接替换已准备的列表。因此移除该重复 stop，
保留加载中旧请求的 abort 回应和 idle/error 时所需的 prepare，不启用追加实验。

`tool/compare_android_inplace_switch.cjs` 对仅相差该 stop 的两个 APK 做对照。
QQ/网易各两首先解析，再将相同 URL/headers 保留在 Node 内存跨 APK 复用，报告
只输出 SHA-256。相同模拟器配置、同一加载配置、关闭缓存，每平台每实现三次。
十二次均确认 preload_buffered=true、实际对象一致、ready/playing、单项列表
和进度推进，并出现原生音频推进回调。

| 平台 | 旧 stop ready 中位数 | 直接替换 ready 中位数 | 旧 stop 音频推进中位数 | 直接替换音频推进中位数 |
| --- | ---: | ---: | ---: | ---: |
| QQ | 208 ms | 113 ms | 352 ms | 250 ms |
| 网易 | 192 ms | 129 ms | 349 ms | 254 ms |

所有六对 ready 均改善，但本轮采用先旧后新的顺序、小样本且为模拟器，不把
约百毫秒收益扩大成秒级根治。该证据说明重复 stop 确实有成本，但不能单独解释
此前完整业务中的 1～2 秒额外等待。证据为 `inplace-same-link-comparison*`。

修改后的首次业务 QQ/网易预备手动切歌分别为 987/424 ms；这次测量发生在
恢复快照后的 swiftshader 配置，不能直接和此前 host GPU 组比较归因。
受控故障回归中的替换路径，坏预取隔离、激活 403（25 ms 返回）、正常源恢复、
连续三次切换及暂停意图保持均通过，见 `inplace-native-recovery*`。
原生九项缓存策略/逐出测试通过；调试构建成功。

安装测试发生过一次签名不匹配后的 Flutter 自动卸载。随后从
2026-10-12 的模拟器快照恢复登录记录与音源配置，备份 shared_prefs，并核对
证书后用匹配签名的 debug APK 覆盖安装。此后安装脚本仅使用 adb install -r，
失败即停止，没有卸载回退。快照后的本地状态不能据此声称完整恢复。

## 业务等待的进一步收尾

恢复原 host GPU、单核模拟器配置，动态启用 Dart CPU profiler 后再次运行完整
播放器页面的 QQ/网易混合队列。4776 个样本中，drawFrame 链包含约 2187 个，
buildScope 约 1289 个，flushLayout 约 890 个（包含关系，不能相加）。没有
证据把主要耗时归到 QuickJS 运算。一次冷启动观察到单帧 build 5.5 秒，但暖态
没有稳定重复，因此不把该异常归因为某个已确认的业务热点。

页面 opaque=true 的对照没有稳定改善（预备手动切歌 1035 ms，对照 921 ms），
不修改生产路由透明行为，也不启用默认追加。保留三项有明确依据的修复：

- Android 原生 load 直接替换源，移除重复 stop；同链接收益见上表。
- MobilePlayerPage 不在 build 中发送系统全屏命令，仅在所需模式变化时发送。
  横竖屏、歌词样式、无关依赖变化的 widget 回归通过。
- 同播放代次/队列项/预取代次的重复 playing 通知，不重置已安排的预取定时器。
  持续每 200 ms 发送 playing 的回归中，下一首仍在四秒内准备；暂停和显式
  失效仍取消定时器，保留 2.5 秒退避策略，不提高后台请求并发。

最终混合业务验证 `business-inplace-final-mixed-*`：首次 2474 ms、一秒后未预载
切歌 3310 ms、预备手动切歌 550 ms（native source future 373 ms）、自动切歌
1900 ms、连续点选 1832 ms。自动项包含 seek 和剩余曲长，不能当作纯接管耗时。
进度推进、暂停/恢复、临近结束的手动目标保护全部通过，pending/error 清空。
前两轮预备手动切歌分别为 921/1035 ms；这些业务轮次不是同 URL 的严格配对，
不能把单次 550 ms 全归因于最后两项改动，也不能声称所有冷切歌已秒开。

86 项相关回归通过，静态检查无问题。测试使用静音调试版，证明状态、原生
音频回调和进度，不等于实机外放听感验收。最终 debug APK 构建成功，核对
证书后 adb install -r 覆盖安装成功，重新启动应用；该次覆盖安装保留现有配置。

## 当前版本：恢复官方插件

以上涉及原生预缓冲、分片缓存、去掉 stop 和追加切歌的内容均为历史实验。
按用户要求，依赖改为 pub.dev 官方 just_audio 0.10.6，不再使用本地覆盖或
定制 Media3。官方 stop/prepare 行为完整保留；Android 保留单原生音源，
下一首仅预取链接和歌词，不把预取成功记为原生缓冲命中。旧插件及专用实验
脚本已移至 build/retired-just-audio-extension，可恢复，不随项目发布。
详细现状见 android-native-playback.md。

官方版迁移验证：367 项测试通过，6 项原生脚本测试按默认配置跳过；静态检查
无问题；Android debug 构建、同证书覆盖安装通过，依赖图解析到 Media3 1.4.1。
首次冷态业务验证发生一次 load_source 约 7.4 秒超时，pending 已清空；原因
尚未确认，不把它掩盖为通过。后续关闭缓存和保持缓存开启的两轮完整 QQ/网易
混合队列均通过，包括进度、连续点选、暂停恢复、临近结束手动目标保护。
链接预取后的手动切歌分别 1370/1618 ms；此时 prepared=false，没有原生
预缓冲。首次/冷切歌仍出现约 2.4～5 秒等待，不声称升级消除了所有加载超时。
证据为 official-just-audio-mixed-*、official-just-audio-mixed-r2-*、
official-just-audio-cache-enabled-*，均保存在 build/。
